Mission

Make it a cartridge, not a web app

Dungeonlike is a small, fully-working browser roguelike. The logic is done — the visuals don't exist yet. Today the dungeon is raw ASCII in a <pre> and every other screen is unstyled HTML. Give it the look and feel of a Game Boy Advance dungeon-crawler: chunky, warm, high-contrast, legible-at-a-glance.

North star: A cozy-but-dangerous SRD dungeon crawl that looks like it shipped on a GBA cartridge.

Steal the UI language from these:

Golden Sun Fire Emblem (GBA) FF Tactics Advance Pokémon Emerald The Minish Cap Advance Wars

What we're dressing

Five screens, one small roster

The renderer switches on state.mode. This is the entire content set — size the art work to it.

Roster to illustrate

  • 3 classes — Fighter (Longsword / Second Wind), Wizard (Fire Bolt / Ray of Frost), Rogue (Rapier / Sneak Attack)
  • 5 monsters — Goblin, Skeleton, Giant Rat, Kobold, Orc
  • 1 item — Potion of Healing
  • Dungeon tiles — wall, floor, stairs-down, player

Four damage types

Each wants its own color and icon shape — never color alone.

Slashing Piercing Fire Cold

Dungeon grid is 40 × 20 tiles. Battles are 1-v-1, turn-based, Pokémon-style.

System · Type

Pixel-crisp, two roles

Everything renders at native pixel size or integer multiples — no anti-aliasing, no fractional scaling. A 1px hard drop-shadow keeps text legible over dungeon art. Stats and combat numbers get a tabular treatment so they don't jitter as they change.

Feel & care

Snappy, cheap, legible

Motion — all CSS, no engine

  • Transitions: hard cut or a 4–6 frame fade/wipe — no smooth slides
  • Cursor blinks ~2Hz; snaps tile-to-tile
  • Log text crawls ~30–60 chars/sec, snaps in on keypress
  • HP bar drain — the one continuous tween (~300–500ms)
  • Hits: white/red flash + a few-px shake + floating number, all ≤300ms

Accessibility

  • 1px ink-shadow on all text over dungeon art
  • Never color-alone: HP shows numeric cur/max; damage types carry an icon shape
  • Focus always visible — gold cursor + selected bevel
  • Integer-scale the 240×160 virtual screen so pixels stay crisp on high-DPI
  • Every action works by keyboard (arrows/WASD + Enter, already wired) and pointer
  • Honor prefers-reduced-motion

Guardrails

Do / Don't

Do

  • Frame everything in beveled window boxes — chrome that feels physical
  • Commit to a small, saturated palette and reuse it religiously
  • Keep pixels square and crisp at every scale
  • Make HP, damage & stats read instantly and animate satisfyingly
  • Add torchlight, mood, and a little grime

Don't

  • Ship flat modern web UI, thin borders, or soft drop shadows
  • Use emoji, system fonts, or anti-aliased "smooth" scaling
  • Go full NES/8-bit blocky — we're 16-bit, richer shading
  • Rely on color alone for HP or damage-type meaning
  • Touch game rules, dice math, or the state machine

The ask

Deliverables for the pass

  • ☐Locked palette tokens + theme.css
  • ☐Chosen + self-hosted pixel font(s): body + display
  • ☐UI kit: window box · menu + cursor · HP bar · stat chip · command menu · message window
  • ☐16×16 tile set: wall (+ variants) · floor (+ alt) · stairs · fog
  • ☐Sprites: player (×3 class tints) · 5 monsters · potion · icon set (AC / HP / dice / 4 damage types)
  • ☐Portraits: 3 classes, 5 monsters (battle + select busts)
  • ☐Screen comps: Title · Character Select · Dungeon · Battle · Victory · Game Over
  • ☐Motion spec applied: transitions · cursor blink · HP drain · hit flash / shake / floating numbers
  • ☐Accessibility check: contrast · non-color-coded meaning · visible focus

Implementation stays in src/components/* + CSS/assets — React 18 + Vite + TypeScript, no new game framework. Preserve the existing data-testids (dungeon-grid, battle-log) and button names, or update tests in lockstep. The monster/item glyph fields already in the data map cleanly to sprite indices — keep the renderer data-driven.
